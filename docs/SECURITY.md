# Меры обеспечения безопасности

## Защита Auditor

В текущей реализации Auditor используются:

* защитные HTTP-заголовки и CSP;
* ограничение разрешённых CORS-источников;
* CSRF-защита HTML-форм;
* API-аутентификация с использованием API-ключей;
* аутентификация пользователей и разграничение доступа по ролям;
* ограничение частоты запросов с ответом HTTP `429`;
* журналирование HTTP-запросов и `X-Request-Id` для трассировки.

## Сессии и cookies

Пользовательские сессии Auditor используют защитные атрибуты cookies:

* `HttpOnly`;
* `SameSite=Lax`;
* `Secure` при работе через HTTPS.

Лабораторное `target`-приложение намеренно содержит небезопасные cookie-сценарии. Они используются для проверки правил Auditor и не относятся к защите самого Auditor.

## TLS

Основные компоненты стенда работают по HTTPS:

* Auditor — `:5000`;
* mitmproxy — `:443`;
* target — HTTPS внутри Docker-сети.

В локальной лаборатории используются тестовые сертификаты. Nginx в текущей архитектуре не используется.

## Аудит токенов и сессий

Auditor обнаруживает, в частности:

* токены в URL;
* небезопасные cookie;
* повторное использование токенов разными клиентами;
* использование истёкших токенов;
* изменение географической метки;
* session hijacking;
* session fixation.

Чувствительные значения могут представляться в виде fingerprint или ограниченного preview. Fingerprint не является шифрованием и не позволяет восстановить исходное значение.

## Географический анализ

Для лабораторного анализа используется HTTP-заголовок:

```text
X-Country
```

Поэтому географическое изменение является демонстрационной корреляцией событий, а не полноценной геолокацией. В production источник такой информации должен быть доверенным.

## Изоляция и hardening Docker

Сервисы работают в отдельной Docker-сети `lab`.

Порт `9100` `node-exporter` и порт target не публикуются на хост.

Основные контейнеры используют:

* непривилегированного пользователя;
* `no-new-privileges`;
* `cap_drop: ALL`;
* минимально необходимые capabilities;
* read-only подключение сертификатов.

## Защита секретов

Секреты и API-ключи не должны храниться в Git.

В частности:

```text
.env
.env.docker
*.key
*.db
```

не должны коммититься.

API-ключи Auditor хранятся в базе в хешированном виде. Локальные секреты передаются через переменные окружения и локальные конфигурации.

## Мониторинг

Состояние системы контролируется через:

```text
Auditor ───────► Prometheus ───────► Grafana
node-exporter ─► Prometheus ───────► Grafana
```

Auditor предоставляет application metrics через `/metrics`, а `node-exporter` — системные метрики.

## Ограничения

Система является лабораторным инструментом:

* SQLite не предназначен для высоконагруженного production;
* тестовые TLS-сертификаты предназначены для локальной среды;
* target содержит намеренно уязвимые сценарии;
* географический анализ основан на клиентской метке;
* Attack Simulator предназначен только для разрешённых целей;
* отключение TLS-проверки в локальных сценариях симулятора не следует использовать для недоверенных внешних соединений.

## Production

При переносе системы в production необходимо заменить лабораторные сертификаты и тестовые секреты, использовать подходящее постоянное хранилище, ограничить доступ к административным интерфейсам и организовать централизованное управление секретами, журналами и обновлениями.

Дополнительные средства защиты, такие как WAF и SIEM, могут использоваться в зависимости от требований инфраструктуры.
